# previs-lite: playbook for Claude

This repo is a light LED previsualiser. The user will usually ask you to set up a **new venue**: they give you a Resolume Advanced Output XML (the pixel map), photos of the space, and some measurements or a description. You turn that into a project, then they match the photos in the app. Read `README.md` and `docs/PROJECT_FORMAT.md` first if you have not.

## Rules of the repo

- Python 3 standard library only. No pip installs, no build step. The app is plain JS modules + WebGL in `app/`.
- **Fonts:** `app/fonts/NeueMachina*` is a commercial font that must never be committed or published (it is git-ignored). Manrope is open (OFL) and is committed. Do not add other font files without checking their licence.
- Do not add dependencies. Do not commit large videos or full-resolution photos unless the user says so (resize photos to about 2000 px on the long edge).
- Never overwrite `projects/demo-wall/` (it is the public example, regenerated by `tools/make_demo.py`). New venues get their own folder. Client projects must not go into a public repo: ask where they should be kept.
- Run `node tests/math.test.mjs` after touching `app/js/math.js`. Run `python3 previs.py check NAME` after touching a project.

## Setting up a new venue

1. **Read the XML.** `python3 previs.py new NAME --xml FILE.xml` prints the screens and slice counts it finds. Use `--screen "NAME"` (repeatable) to keep only the LED screens, not projection or preview screens. A slice's *Name* is what the positions CSV must match.
2. **Get positions.** Ask the user for what they have (drawing, measurements, a rig plan, panel counts and spacing, photos). Decide an origin and use metres, x east, y north (back of room), z up. Write `sources/panels.csv` with `slice_name,x_m,y_m,z_m,w_m,h_m,nx,ny,nz,ux,uy,uz`. Generate it with a short Python script when panels follow a pattern (grids, towers, curves); put the script next to the CSV so it can be re-run. If they have no positions yet, create the project without `--positions` (flat wall from the pixel map) and tell them it is a placeholder.
3. **Panel orientation.** `normal` = the way the face points (towards the audience). `up` = the way the top of the image points. Get this right: if a look runs the wrong way on screen, the usual cause is `up` or a mirrored slice `uv`, not the camera. Say what you assumed.
4. **Build the model** from the photos and measurements: either an OBJ (the user can drop it on the app; write it in metres, Z up, in the same frame as the panels, and they will not need to touch Units or Up axis) or a `model.json` of line segments. It only needs to contain what is clearly visible and findable in the photos: floor corners, walls, doors, stage, truss, pillars, the LED structure. For `model.json` use `tools/modeling.py` (`Model.box`, `grid_floor`, `truss_tower`, ...). Estimate sizes from known references in the photos (a door is about 2.0 m high, a step 0.18 m, a truss box 0.3 m, a pallet 1.2 x 0.8 m) and tell the user which numbers are estimates. Keep it light: tens to a few hundred segments.
5. **Check.** `python3 previs.py check NAME` must say OK. Then `python3 previs.py serve --open`, open the project in the browser and look at the orbit camera: do the panels sit where the rig is? Check orientation with the test pattern (it draws each panel's id and a moving highlight).
6. **Photos.** Resize and put them in `projects/NAME/photos/`, then add a camera entry for each (or let the user drop them into the app):
   `{"name": "From the door", "type": "photo", "photo": "photos/door.jpg", "size": [w, h], "P": null}`.
   The user presses **Match camera** and clicks pairs. Tell them which features to click: pick 8 or more points spread over the whole photo and at different depths and heights, using corners that are crisp in both the model and the photo. Below 3 px typical error is good; if it is worse, a pair is wrong (drag it, or remove its chip) or the model is off in that area (fix `model.json`).
7. **Commit** the project folder (`project.json`, `model.json`, `sources/`, resized `photos/`).

## If you can drive the browser

You can test the app yourself. It exposes `window.previs = { S, R }` (state and renderers) in the console. The camera matcher can be exercised with synthetic mouse events on `#oRef` (3D view) and `#oPhoto` (photo); see how the solver was verified in the history of this repo. For a photo-matched camera, `S.proj.cameras[i].P` is the 3x4 matrix and `rms` the error.

## Live from Resolume

`python3 previs.py serve --live` receives an NDI output (the user enables NDI in Resolume: Preferences > Video). The app asks the bridge for the source and puts frames on the screen's panels. The frame size must match the screen's pixel map (slice `uv` are in those pixels). If no source appears, check that Resolume's NDI output is on, both machines are on the same network (or the same machine), and the OS allowed local network access for Python.

## Style

Keep answers and commit messages plain and short. Prefer fixing the data (`project.json`, `panels.csv`, `model.json`) over adding special cases to the app.
